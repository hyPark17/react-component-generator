# TDD Rule

> **이 규칙은 Rigid(고정) 이다. 상황에 맞게 변형하지 마라.** 예외를 판단하지 말고 아래 기준표대로만 적용하라.

## 0. 우선순위 (Fallback 조항)

이 파일은 **기본값(fallback)** 이다. 프로젝트 루트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시되어 있다면 **그 규칙이 이 파일보다 우선**한다. 충돌이 없는 항목에 한해서만 이 파일을 적용하라.

## 1. 적용 기준

**TDD 반드시 적용 (RED부터 시작):**
- 비즈니스 로직 (계산, 상태 전이, 조건 분기)
- API 엔드포인트 / 서버 핸들러
- 유틸리티 함수 (순수 함수, 파서, 포매터)
- 버그 수정 (재현 테스트 → 수정)

**TDD 불필요 (바로 작성 가능):**
- 타입 정의 (interface, type alias)
- 설정 파일 (config, env, build script)
- 순수 UI 마크업 (로직 없는 프레젠테이셔널 컴포넌트)
- SQL 스키마/마이그레이션

판단이 애매한 대상은 **"적용" 쪽으로 분류**하라.

## 2. RED-GREEN-REFACTOR 사이클

### RED
- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 마라.
- 테스트 작성 후 **반드시 실행해서 실패를 눈으로 확인**하라. 실행하지 않고 다음 단계로 넘어가는 것은 금지.
- 실패 이유는 **오직 "기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타로 인한 실패는 RED로 인정하지 않는다 — 고치고 다시 실행하라.

### GREEN
- **테스트를 통과시키는 최소한의 코드만** 작성하라. **YAGNI** — 지금 테스트가 요구하지 않는 기능/분기/파라미터는 추가하지 마라.
- 신규 테스트와 **기존 테스트 전체가 모두 통과**하는지 확인한 뒤에만 다음 단계로 진행하라.

### REFACTOR
- 중복 제거, 이름 개선, 헬퍼 추출만 수행하라.
- 전체 테스트가 **계속 green을 유지**하는지 매 변경마다 확인하라.
- **새로운 동작을 추가하지 마라.** 새 동작이 필요하면 REFACTOR를 멈추고 다음 RED로 넘어가라.

### 반복
- 다음 동작이 남아 있다면 **다음 동작에 대한 RED로 돌아가라.** 사이클을 건너뛰지 마라.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 **먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작**하라.
- "일단 참고용으로 남겨둔다"는 명목으로 미테스트 코드를 유지하는 것도 **금지**한다. 삭제 후 재작성이 유일한 경로다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| 너무 단순해서 테스트 불필요 | 단순한 코드일수록 테스트 작성 비용도 낮다. 단순함은 생략의 근거가 아니다. |
| 나중에 추가하겠다 | "나중"은 오지 않는다. GREEN 이후 테스트 없는 코드는 그대로 방치된다. |
| 시간이 없다 | 디버깅 없이 GREEN까지 가는 TDD가 사후 디버깅보다 총 시간이 짧다. |
| 삭제하면 낭비다 | 검증되지 않은 코드는 자산이 아니라 리스크다. 낭비는 버그가 프로덕션에 나가는 것이다. |
| 프로토타입이다 | 프로토타입도 결국 머지되거나 기반이 된다. 예외 취급하지 마라. |

## 5. 산출물 형식

각 사이클 단계마다 어떤 단계인지(RED/GREEN/REFACTOR) 명시하고, 실행한 테스트 명령과 결과(실패/통과)를 함께 보고하라.
