# commit: 변경사항 분석·커밋

현재 작업 디렉토리의 git 저장소를 기준으로, 변경사항을 분석해 논리적 단위로 나누고 컨벤션에 맞는 한국어 커밋 메시지를 작성해 바로 커밋한다. 승인을 구하려고 멈추지 않는다.

## 워크플로우

### Step 0: 저장소 지침 확인

저장소 루트에 `AGENTS.md` 또는 `CLAUDE.md`가 있으면 읽고, 커밋 메시지 포맷이나 컨벤션이 명시돼 있으면 그것을 최우선으로 따른다. 없으면 이 스킬의 기본 컨벤션(Step 2)을 사용한다.

### Step 1: 변경사항 분석

- `git status`로 변경/추가/삭제된 파일 전체를 확인한다.
- `git diff` (staged 변경이 있으면 `git diff --cached`도 함께)로 실제 내용을 분석한다.
- `git log --oneline -20`으로 기존 커밋 메시지 스타일이 있으면 참고한다(있으면 그 스타일을 우선한다).
- 시크릿·자격증명으로 보이는 파일(`.env`, `credentials.json` 등)이 스테이징 대상에 있으면 사용자에게 경고하고 기본적으로 제외한다.

### Step 2: 논리적 단위로 분류

- 변경사항을 하나의 목적을 가진 단위로 묶는다. 서로 무관한 변경(예: 기능 추가 + 포맷팅만 바뀐 파일)은 별도 커밋으로 나눈다.
- 분류가 애매한 경우에도 묻지 않고 가장 합리적인 단위로 스스로 나눈다(관련성이 높은 파일끼리 묶고, 근거가 약하면 하나의 커밋으로 합친다).
- 각 단위에 대해 타입을 정한다:
  - `feat`: 새로운 기능 추가
  - `fix`: 버그 수정
  - `refactor`: 동작 변화 없는 코드 구조 개선
  - `chore`: 빌드/설정/의존성 등 잡무성 변경
  - 그 외 필요 시 `docs`, `test`, `style` 등 저장소 관례에 맞춰 사용

### Step 3: 커밋 메시지 작성 (한국어)

형식: `{type}: {요약}`

- 요약은 한 줄, 명령형·현재형으로 간결하게 작성한다("~함", "~했음" 같은 서술형 대신 "~수정", "~추가" 형태).
- 왜(why)가 코드만으로 드러나지 않는 경우에만 본문에 짧게 근거를 덧붙인다. 코드가 스스로 설명하는 내용(무엇을 바꿨는지)은 반복하지 않는다.
- 커밋 메시지에 이 스킬이나 현재 작업 세션을 언급하지 않는다.
- 여러 커밋으로 나눴다면 각 커밋마다 이 형식을 적용한다.

### Step 4: 즉시 커밋

- 승인을 구하지 않고 바로 진행한다. 커밋 단위별로 관련 파일만 `git add`한 뒤 커밋한다. `git add -A`/`git add .`처럼 전체를 한 번에 올리지 않는다.
- 시크릿·자격증명으로 보이는 파일은 Step 1에서 확인한 대로 제외하고 진행하며, 제외했다는 사실만 결과 보고에 남긴다.
- 커밋 후 `git log --oneline -n {커밋 수}`와 `git status`로 결과를 확인하고, 생성된 커밋 목록(해시·메시지)을 사용자에게 보고한다.
- push는 별도로 명시적인 요청이 있을 때만 수행한다(자동 push 금지).
